01 · Foundation

The Boot Process

What actually happens between pressing the power button and your OS running. Every layer, no hand-waving.

Power-On: The First Instruction

The moment power is applied, the CPU is in a known, hard-wired state. On x86, the instruction pointer CS:IP is set to 0xFFFF:0x0000, which in 16-bit real mode resolves to physical address 0xFFFF0. That's 16 bytes below the top of the first megabyte of address space.

At that address sits a JMP instruction — placed there by your motherboard firmware (BIOS or UEFI). It jumps to the actual firmware code, typically somewhere in the high flash ROM. The CPU has no idea what OS you're running. It doesn't care. It just executes the instruction at that address.

Why 0xFFFF0? After a reset, the CPU drives CS to 0xF000 with an internal base of 0xFFFF0000 (in 80386+). The real mode segment:offset pair 0xFFFF:0x0000 evaluates to 0xFFFF0. The first instructions are in ROM — ROM that exists at the top of the 1MB + a bit of extended space.

POST (Power-On Self Test)

Before anything useful happens, the BIOS runs POST. It's not magic — it's just a checklist:

  • Test CPU registers and basic instruction execution
  • Verify CMOS checksum (BIOS settings stored in battery-backed SRAM)
  • Initialize the memory controller and test RAM (that memory count you used to watch tick up)
  • Initialize buses: PCI, PCIe, USB
  • Enumerate and initialize hardware: IDE, SATA, NVMe controllers
  • Set up the Interrupt Vector Table (IVT) at address 0x0000

The Boot Device Search

After POST, the BIOS checks its configured boot order. It looks for a bootable device. For a disk, "bootable" is brutally simple: read the first 512 bytes. If the last two bytes are 0x55 and 0xAA — it's bootable. That's it. That's the entire check.

The 0x55AA signature is at bytes 510 and 511 (0-indexed), i.e., the last two bytes of the 512-byte sector. The BIOS loads those 512 bytes to address 0x7C00 and jumps to it. Your bootloader now has control.

Why 0x7C00?

The BIOS loads your MBR to physical address 0x7C00. Why this specific address? Historical accident. On the IBM PC (8088, 1981), this was the highest point where a 512-byte bootloader could live without overwriting itself or the BIOS data area, while still leaving the first 32KB for the OS. The original PC had 32KB of usable RAM. 0x7C00 = 0x8000 - 0x0200 (512 bytes).

02 · Foundation

Real Mode

The CPU's initial operating mode. 16-bit registers, segmented addressing, 1MB address space. Where you start.

What Real Mode Actually Is

When your CPU boots, it starts in real mode — the mode where the CPU behaves essentially like an 8086 from 1978. No memory protection. No privilege levels. No paging. Any code can read or write any memory, including the IVT and BIOS data area. It's raw hardware access.

You have 16-bit registers and you can only directly address 1 MB of memory. The reason for this limit: the address bus on the original 8086 was 20 bits wide. 2²⁰ = 1,048,576 bytes = 1 MB. Modern CPUs still start in this mode for backward compatibility.

Registers in Real Mode

Register(s) Name Width Purpose
AX, BX, CX, DX General Purpose 16-bit Arithmetic, data. Split into AH/AL, BH/BL etc. AX=accumulator, CX=counter, DX=data/I/O, BX=base.
SI, DI Index 16-bit Source Index, Destination Index. Used for string ops (MOVSB, LODSB etc.).
BP, SP Pointer 16-bit Base Pointer and Stack Pointer. BP references stack frame, SP tracks top of stack.
CS, DS, ES, SS Segment 16-bit Code, Data, Extra, Stack segments. Define 64KB windows into memory.
IP Instruction Pointer 16-bit Offset within CS segment. You can't directly write IP — only JMP/CALL/RET affect it.
FLAGS Flags Register 16-bit CF (carry), ZF (zero), SF (sign), OF (overflow), IF (interrupt enable), DF (direction).

Segmented Addressing: The Core Mechanic

Real mode uses a segment:offset addressing scheme. Physical address is computed as:

formula 
Physical Address = (Segment × 16) + Offset
                   = (Segment << 4) + Offset

Segment is shifted left by 4 bits (multiplied by 16), then the offset is added. Both are 16-bit values. The result is a 20-bit physical address.

Example: CS = 0x07C0, IP = 0x0000 → Physical = 0x07C0 × 16 + 0 = 0x07C00. This is why the BIOS often jumps to 0x07C0:0x0000 — same physical address as 0x0000:0x7C00.

Aliasing alert: Multiple segment:offset pairs map to the same physical address. 0x0000:0x7C00, 0x07C0:0x0000, and 0x07B0:0x0100 all point to physical 0x7C00. This matters when you call far procedures or rely on CS for data access.

Stack in Real Mode

The stack uses SS:SP. The x86 stack grows downward. PUSH decrements SP by 2 then writes. POP reads then increments. You need to set up your own stack — the BIOS gives you one but you shouldn't rely on it. Common setup:

x86 NASM · real mode stack setup 
; Set up stack at 0x0000:0x7BFF (just below our code)
cli                         ; Disable interrupts during stack setup
xor  ax, ax
mov  ss, ax               ; SS = 0x0000
mov  sp, 0x7C00            ; SP = 0x7C00 — stack grows down from here
sti                         ; Re-enable interrupts

Real Mode Limitations

  • Max 1 MB addressable — 20-bit address bus. Segment 0xFFFF + offset 0xFFFF = 0x10FFEF (wraps around!)
  • No memory protection — all code runs at the same privilege level. Any bug can overwrite interrupt vectors.
  • No multitasking — single flat execution context.
  • Max 64 KB per segment — 16-bit offset. You need multiple segments to access more.
  • BIOS interrupts only — the only way to talk to hardware (disk, video) is via BIOS INT calls.

A Minimal Real Mode Program

x86 NASM · minimal bootloader skeleton 
[BITS 16]
[ORG 0x7C00]

start:
    ; Clear segment registers — BIOS may leave them dirty
    cli
    xor  ax, ax
    mov  ds, ax
    mov  es, ax
    mov  ss, ax
    mov  sp, 0x7C00
    sti

    ; Print a character using BIOS INT 10h
    mov  ah, 0x0E        ; TTY output function
    mov  al, '!'
    int  0x10

.halt:
    hlt
    jmp  .halt          ; Loop in case of NMI waking us

; Padding and boot signature
times 510 - ($ - $$) db 0
dw 0xAA55              ; Note: little-endian, stored as 55 AA on disk
ORG directive: [ORG 0x7C00] tells NASM that this code will be loaded at offset 0x7C00. It doesn't move anything — it just adjusts address calculations for labels so jmp label generates the correct address.

446 bytes, not 512. If you're building a real bootloader, you have 446 bytes for code. The rest is partition table + signature. In practice, for a learning bootloader without a partition table, you get all 510 bytes — but the moment you add MBR partitioning, you lose 64 bytes.

The Boot Signature: 0x55AA

The last two bytes of the MBR must be 0x55 followed by 0xAA. In x86 little-endian storage, this means the 16-bit word at offset 0x1FE is 0xAA55. The BIOS checks this before jumping to 0x7C00. If it's wrong, the BIOS skips this device entirely.

Partition Table Entry Structure

partition entry · 16 bytes 
; Each partition entry is 16 bytes:
struc partition_entry
    .status      resb 1    ; 0x80 = bootable, 0x00 = not bootable
    .chs_start   resb 3    ; CHS address of first sector (legacy, mostly ignored)
    .type        resb 1    ; Partition type: 0x83=Linux, 0x0B=FAT32, 0x82=swap...
    .chs_end     resb 3    ; CHS address of last sector (legacy)
    .lba_start   resd 1    ; LBA of first sector (USE THIS, not CHS)
    .sector_cnt  resd 1    ; Total sectors in partition
endstruc

Why Stage 2 Is Necessary

446 bytes is not enough to load a kernel. You can't even implement a basic FAT32 driver in 446 bytes. The MBR's only job is to:

  • Find the active (bootable) partition
  • Read Stage 2 from a known location on disk into memory
  • Jump to Stage 2

Stage 2 can be as large as you want — typically loaded at 0x7E00 (right after the MBR in memory). It has the space to enable A20, set up the GDT, switch to 32-bit protected mode, parse the filesystem, and load the kernel.

A Real MBR: Loading Stage 2

x86 NASM · MBR loading stage 2 via LBA 
[BITS 16]
[ORG 0x7C00]

mbr_start:
    cli
    xor   ax, ax
    mov   ds, ax
    mov   es, ax
    mov   ss, ax
    mov   sp, 0x7C00
    sti
    mov   [boot_drive], dl  ; BIOS passes drive number in DL

    ; Load 4 sectors (2KB) starting at LBA 1, to 0x7E00
    mov   si, dap             ; DS:SI points to Disk Address Packet
    mov   ah, 0x42           ; INT 13h AH=0x42 = Extended Read (LBA)
    mov   dl, [boot_drive]
    int   0x13
    jc    disk_error          ; CF set on error

    jmp   0x0000:0x7E00       ; Far jump to Stage 2

disk_error:
    hlt

; Disk Address Packet (DAP) for INT 13h extended read
dap:
    db 0x10         ; Size of DAP = 16 bytes
    db 0x00         ; Reserved, must be 0
    dw 4            ; Number of sectors to read
    dw 0x7E00       ; Destination offset
    dw 0x0000       ; Destination segment
    dq 1            ; LBA of first sector to read (sector 1, right after MBR)

boot_drive:
    db 0

times 446 - ($ - $$) db 0   ; Pad to partition table
times 64 db 0               ; Empty partition table
dw 0xAA55
Key insight: Save the boot drive number from DL immediately. The BIOS passes it in DL before jumping to 0x7C00, but the moment you call any BIOS INT, DL may be clobbered. Store it and use it for all subsequent disk operations.
04 · BIOS & I/O

BIOS Interrupts

Your only interface to hardware in real mode. Know these cold — they're the API of 1981.

How INT Works

The x86 INT n instruction pushes FLAGS, CS, and IP onto the stack, then looks up vector n in the Interrupt Vector Table at physical address 0x0000. Each entry is 4 bytes: a 16-bit offset followed by a 16-bit segment. The CPU jumps to that segment:offset — that's the BIOS handler. IRET at the end pops CS, IP, and FLAGS, returning to your code.

The IVT occupies the first 1024 bytes of memory (256 vectors × 4 bytes). It lives at 0x0000:0x0000. You can actually overwrite BIOS interrupt handlers — but unless you're writing your own BIOS, don't.

INT 10h — Video Services

AH Function Input Output
0x00 Set video mode AL = mode (0x03 = 80×25 text, 0x12 = 640×480 VGA) —
0x0E TTY write char AL = char, BH = page, BL = color Cursor advances automatically
0x02 Set cursor pos BH = page, DH = row, DL = col —
0x0F Get video mode — AH = columns, AL = mode, BH = page
x86 NASM · print a null-terminated string 
; Input: SI = pointer to null-terminated string
print_str:
    push  ax
    push  bx
    mov   ah, 0x0E
    xor   bx, bx      ; Page 0, foreground color irrelevant in text mode
.loop:
    lodsb              ; AL = [DS:SI], SI++
    test  al, al       ; Check for null terminator
    jz    .done
    int   0x10
    jmp   .loop
.done:
    pop   bx
    pop   ax
    ret

INT 13h — Disk Services

AH Function Key Inputs
0x00 Reset disk controller DL = drive
0x02 Read sectors (CHS) AL=count, CH=cylinder, CL=sector(1-63), DH=head, DL=drive, ES:BX=buffer
0x41 Check INT 13h extensions BX=0x55AA, DL=drive → CF clear if supported
0x42 Extended Read (LBA) DS:SI = pointer to DAP (Disk Address Packet), DL=drive
0x48 Get drive parameters (ext) DS:SI = result buffer, DL=drive → geometry info
Always use LBA (INT 13h AH=0x42) not CHS (AH=0x02). CHS addressing breaks beyond 8 GB and the cylinder/head/sector encoding is a historical disaster. Check for extension support with AH=0x41 first, but any remotely modern BIOS supports it.

INT 15h — System Services

The most important function for bootloaders:

AX Function Purpose
0xE820 Get Memory Map The only reliable way to discover installed RAM. CRITICAL — do this before entering protected mode.
0xE801 Get Extended Memory Older method. Returns memory in 1KB and 64KB blocks. Less detailed than E820.
0x88 Get Extended Memory (KB) Returns KB above 1MB. Oldest method. Max ~64MB. Avoid.
x86 NASM · INT 15h E820 memory map enumeration 
; Build a memory map at 0x8000
; Returns: [0x8004] = number of entries
get_memory_map:
    xor   ebx, ebx       ; EBX = 0 for first call, BIOS fills continuation value
    xor   bp, bp         ; BP = entry count
    mov   es, bp
    mov   di, 0x8000      ; Write entries starting at ES:DI = 0x8000
    mov   edx, 0x0534D4150 ; Magic: "SMAP"
.loop:
    mov   eax, 0xE820      ; Function number
    mov   [es:di + 20], dword 1  ; ACPI 3.0 extended attributes field
    mov   ecx, 24          ; Entry size in bytes
    int   0x15
    jc    .done            ; CF set = error or end
    cmp   eax, 0x0534D4150 ; BIOS must return "SMAP" in EAX
    jne   .done
    test  ecx, ecx
    jz    .skip
    inc   bp              ; Count this entry
    add   di, 24           ; Advance buffer pointer
.skip:
    test  ebx, ebx
    jz    .done            ; EBX = 0 means last entry
    jmp   .loop
.done:
    mov   [0x8004], bp     ; Store count for kernel
    ret
05 · BIOS & I/O

Disk I/O

CHS vs LBA. Reading sectors. Writing reliable disk code that doesn't silently corrupt.

CHS: The Legacy You Must Know

CHS stands for Cylinder, Head, Sector. It's how ancient hard drives physically addressed data:

  • Cylinder: Concentric ring on the disk platter (0 to N-1)
  • Head: Read/write head on the arm (0 to N-1)
  • Sector: Pie-slice of a track — 1-indexed, starts at 1, not 0

CHS was already broken by the early 1990s. INT 13h CHS only supports 10-bit cylinders, 8-bit heads, 6-bit sectors — max ~8 GB. For anything modern, use LBA.

LBA: Logical Block Addressing

LBA treats the disk as a flat array of 512-byte (or 4096-byte) sectors numbered from 0. Sector 0 is the MBR. Sector 1 is the first sector after the MBR. Simple. The conversion from LBA to CHS if you ever need it:

formula · LBA to CHS conversion 
sector    = (LBA % sectors_per_track) + 1
head      = (LBA / sectors_per_track) % num_heads
cylinder  = (LBA / sectors_per_track) / num_heads

Disk Address Packet (DAP)

INT 13h extended read (AH=0x42) takes a pointer to a DAP in DS:SI. The DAP structure:

x86 NASM · DAP structure 
; Disk Address Packet — 16 bytes
struc DAP
    .size         resb 1  ; Size of this structure = 0x10 (16)
    .reserved     resb 1  ; Must be 0
    .count        resw 1  ; Number of sectors to transfer (max ~127)
    .offset       resw 1  ; Transfer buffer offset
    .segment      resw 1  ; Transfer buffer segment
    .lba_lo       resd 1  ; Low 32 bits of 64-bit LBA
    .lba_hi       resd 1  ; High 32 bits (0 for drives <2TB)
endstruc

Robust Disk Read with Retries

Disks fail. BIOS disk functions fail. Always retry. The standard approach: try up to 3 times, reset the controller between attempts.

x86 NASM · disk read with retry 
; Input: SI = DAP pointer, DL = drive number
; Trashes: AX
disk_read:
    mov   cx, 3             ; Retry count
.retry:
    push  cx
    mov   ah, 0x42          ; Extended read
    int   0x13
    pop   cx
    jnc   .success          ; CF clear = success

    ; Read failed — reset controller and retry
    push  cx
    mov   ah, 0x00          ; Reset disk controller
    int   0x13
    pop   cx
    loop  .retry

    ; All retries failed
    jmp   disk_error

.success:
    ret
Reading across a 64KB segment boundary will fail or corrupt data. The BIOS DMA for disk reads can't cross a 64KB segment boundary. If your destination buffer is at 0x7F00 and you read 512 bytes (0x200), you end up at 0x8100 — which crosses the 0x8000 boundary if DS=0. Keep reads within a single 64KB segment or split them.

Loading a Large Bootloader: The Strategy

Your Stage 2 can be loaded anywhere in the first 640 KB (0x0000–0x9FFFF). Common choices:

  • 0x7E00 — Right after MBR. Simple. Stage 2 can be up to ~480 KB here before hitting the EBDA at 0x80000.
  • 0x10000 — 64 KB mark. Clean alignment, plenty of space below 0x80000.
  • 0x20000 — 128 KB mark. Used by some bootloaders to keep away from the IVT/BDA region entirely.
06 · 32-bit Transition

The A20 Line

The most absurd hardware hack in computing history. You must deal with it.

The Problem: Wrap-Around Compatibility

On the 8086, the address bus was 20 bits. Accessing address 0xFFFF:0x0010 computes to 0x100000 (1MB + 16 bytes). But with a 20-bit bus, bit 20 doesn't exist — the address wraps around to 0x00000. Some programs (mostly DOS ones) relied on this wrap-around behavior.

When the 286 arrived with a 24-bit address bus, bit 20 (A20) existed. The wrap-around no longer happened. This broke compatibility. IBM's engineers — in an act of legendary hackery — added a hardware gate on the A20 line, connected to bit 1 of the PS/2 keyboard controller's output port. By default, A20 was disabled (gated off), so the 8086 wrap-around was preserved.

The result: every x86 PC since the 80286 has had this bizarre keyboard-controller-managed address line. You must enable A20 before you can access memory above 1MB in protected mode.

Three Ways to Enable A20

Method 1: BIOS INT 15h

x86 NASM · A20 via BIOS 
mov   ax, 0x2401     ; INT 15h AX=0x2401: Enable A20
int   0x15
jc    .try_keyboard  ; CF set = not supported, try keyboard method

Method 2: Keyboard Controller (the original hack)

x86 NASM · A20 via keyboard controller (Port 0x64/0x60) 
enable_a20_kbd:
    call  kbd_wait_cmd
    mov   al, 0xAD        ; Disable PS/2 port 1 (keyboard)
    out   0x64, al

    call  kbd_wait_cmd
    mov   al, 0xD0        ; Read output port command
    out   0x64, al

    call  kbd_wait_data
    in    al, 0x60        ; Read current output port value
    push  ax              ; Save it

    call  kbd_wait_cmd
    mov   al, 0xD1        ; Write output port command
    out   0x64, al

    call  kbd_wait_cmd
    pop   ax
    or    al, 0x02        ; Set bit 1 = A20 enable
    out   0x60, al        ; Write new output port value

    call  kbd_wait_cmd
    mov   al, 0xAE        ; Re-enable PS/2 port 1
    out   0x64, al
    ret

kbd_wait_cmd:            ; Wait for keyboard controller to be ready for a command
    in    al, 0x64
    test  al, 0x02        ; Bit 1: input buffer full
    jnz   kbd_wait_cmd
    ret

Method 3: Fast A20 (Port 0x92)

x86 NASM · Fast A20 via Port 0x92 
enable_a20_fast:
    in    al, 0x92
    test  al, 0x02        ; Already enabled?
    jnz   .done
    or    al, 0x02
    and   al, 0xFE        ; Clear bit 0 — don't trigger fast reset!
    out   0x92, al
.done:
    ret
Bit 0 of Port 0x92 is the fast reset bit. Setting it reboots the machine. When setting bit 1 (A20), always clear bit 0 first. Getting this wrong means your machine hard-resets the moment you try to enable A20.

Verifying A20 Is Enabled

After enabling, verify it actually worked. Write a known value to a real-mode accessible address, then write a different value to the same physical address via the ≥1MB path. If A20 is still disabled, both accesses alias to the same location. If it's enabled, they're different.

x86 NASM · A20 verification 
; Returns: ZF set if A20 disabled, clear if enabled
check_a20:
    push  es
    push  di
    push  ds
    push  si

    xor   ax, ax
    mov   es, ax
    mov   di, 0x0500      ; ES:DI = 0x0000:0x0500 = physical 0x0500

    mov   ax, 0xFFFF
    mov   ds, ax
    mov   si, 0x0510      ; DS:SI = 0xFFFF:0x0510 = physical 0x100500

    mov   al, [es:di]
    push  ax              ; Save original values
    mov   al, [ds:si]
    push  ax

    mov   byte [es:di], 0x00
    mov   byte [ds:si], 0xFF

    cmp   byte [es:di], 0xFF  ; If equal: A20 off (both alias same address)

    pop   ax               ; Restore values
    mov   [ds:si], al
    pop   ax
    mov   [es:di], al

    pop   si
    pop   ds
    pop   di
    pop   es
    ret
07 · 32-bit Transition

Global Descriptor Table

The hardware data structure that defines memory segments in protected mode. Get this right or triple-fault immediately.

What the GDT Is

In protected mode, segment registers no longer contain physical addresses. They contain selectors — indices into the Global Descriptor Table. The GDT is an array of 8-byte segment descriptors that define the base address, limit, and access rights of each memory segment. The CPU hardware enforces these limits and permissions.

The first entry (index 0) is always the null descriptor — 8 bytes of zeros. Loading any segment register with selector 0 that gets dereferenced causes a General Protection Fault. This is intentional: it catches uninitialized segment register bugs.

Segment Descriptor Layout

Each descriptor is 8 bytes. The layout is intentionally scrambled — historical byte-level compatibility reasons with the 286's 6-byte descriptor format:

segment descriptor · bit layout (8 bytes) 
Bits 63-56:  Base[31:24]       High byte of base address
Bits 55-52:  Flags             G, D/B, L, AVL
Bits 51-48:  Limit[19:16]      High nibble of limit
Bits 47-40:  Access Byte       P, DPL, S, Type
Bits 39-16:  Base[23:0]        Low 3 bytes of base address
Bits 15-0:   Limit[15:0]       Low word of limit

Access Byte breakdown (byte 5):
  Bit 7:   P   — Present (must be 1 for valid descriptor)
  Bits 6-5: DPL — Descriptor Privilege Level (0=kernel, 3=user)
  Bit 4:   S   — Descriptor type (1=code/data, 0=system)
  Bit 3:   E   — Executable (1=code, 0=data)
  Bit 2:   DC  — Direction/Conforming
  Bit 1:   RW  — Readable(code)/Writable(data)
  Bit 0:   A   — Accessed (CPU sets this, you leave it 0)

Flags nibble (bits 55-52):
  Bit 55:  G   — Granularity (0=byte limit, 1=page (4KB) limit)
  Bit 54:  D/B — Default op size (0=16-bit, 1=32-bit)
  Bit 53:  L   — Long mode (1=64-bit code segment)
  Bit 52:  AVL — Available for OS use

A Minimal 32-bit GDT

For a flat 32-bit protected mode setup, you need exactly 3 entries: null descriptor, code segment, data segment.

x86 NASM · GDT for 32-bit protected mode 
gdt_start:

; Descriptor 0: Null — mandatory
gdt_null:
    dq 0

; Descriptor 1: Code segment (selector 0x08)
; Base=0x00000000, Limit=0xFFFFF (×4KB = 4GB), Ring 0, 32-bit
gdt_code:
    dw 0xFFFF     ; Limit[15:0]
    dw 0x0000     ; Base[15:0]
    db 0x00       ; Base[23:16]
    db 0x9A       ; Access: P=1 DPL=00 S=1 E=1 DC=0 RW=1 A=0 → 10011010
    db 0xCF       ; Flags+Limit[19:16]: G=1 D=1 L=0 → 1100 | 1111
    db 0x00       ; Base[31:24]

; Descriptor 2: Data segment (selector 0x10)
; Same span as code, but not executable, writable
gdt_data:
    dw 0xFFFF
    dw 0x0000
    db 0x00
    db 0x92       ; Access: P=1 DPL=00 S=1 E=0 DC=0 RW=1 A=0 → 10010010
    db 0xCF
    db 0x00

gdt_end:

; GDT Descriptor (for LGDT instruction)
gdt_descriptor:
    dw gdt_end - gdt_start - 1  ; Limit: size in bytes minus 1
    dd gdt_start                  ; Base: linear address of GDT

; Segment selectors (index × 8, RPL in bits 1:0)
CODE_SEG equ gdt_code - gdt_start  ; = 0x08
DATA_SEG equ gdt_data - gdt_start  ; = 0x10

RPL
  • Index: Which entry in the GDT (or LDT if TI=1). Entry 1 = index 1 = bits 15:3 = 0x0008. Entry 2 = 0x0010.
  • TI (Table Indicator): 0 = GDT, 1 = LDT (Local Descriptor Table).
  • RPL (Requested Privilege Level): 0 = ring 0, 3 = ring 3. CPU enforces that RPL ≤ descriptor's DPL.
The flat model: Setting both code and data segments to base 0 and limit 4GB (with G=1, limit=0xFFFFF → 0xFFFFF × 4096 = 4GB) means segment registers become irrelevant — you're using a flat address space. This is what every modern OS does. The segmentation hardware is effectively bypassed in favor of paging.
08 · 32-bit Transition

Protected Mode

The switch from 16-bit chaos to 32-bit hardware-enforced memory protection. One bit in CR0. Then a lot of careful work.

What Changes in Protected Mode

  • 32-bit registers — EAX, EBX, ECX, EDX, ESI, EDI, ESP, EBP, EIP
  • Up to 4 GB addressable — with 32-bit registers and a 32-bit address bus
  • Segment registers are selectors — they index into the GDT, not direct memory addresses
  • Memory protection — the CPU enforces segment limits and privilege levels
  • No BIOS interrupts — INT calls go through your IDT, not the IVT. BIOS services are real-mode only.

CR0: Control Register 0

CR0 is a 32-bit control register. Bit 0 (PE — Protection Enable) is the on/off switch for protected mode. Setting it is the actual transition. There's no going back easily (well, technically you can, but that's obscure).

The Exact Switching Sequence

This is the exact order you must follow. Deviate and you triple-fault:

x86 NASM · real mode → protected mode transition 
[BITS 16]

enter_protected_mode:
    ; Step 1: Disable interrupts — no BIOS interrupts in PM
    cli

    ; Step 2: Load GDT — must be done before setting PE bit
    lgdt  [gdt_descriptor]

    ; Step 3: Set PE bit in CR0
    mov   eax, cr0
    or    eax, 0x1          ; Set bit 0 (PE)
    mov   cr0, eax

    ; Step 4: FAR JUMP to flush instruction pipeline and reload CS
    ; The far jump MUST come immediately after setting PE
    ; It loads CS with our 32-bit code segment selector
    jmp   CODE_SEG:pm_entry    ; CODE_SEG = 0x08

[BITS 32]

pm_entry:
    ; Step 5: Update all other segment registers
    ; They still contain old real-mode values
    mov   ax, DATA_SEG         ; DATA_SEG = 0x10
    mov   ds, ax
    mov   es, ax
    mov   fs, ax
    mov   gs, ax
    mov   ss, ax

    ; Step 6: Set up a proper 32-bit stack
    mov   esp, 0x90000       ; Stack at 576 KB mark

    ; We are now in 32-bit protected mode
    ; Full 32-bit registers, hardware-enforced segments
The far jump is mandatory. After setting PE, the CPU's instruction prefetch queue may contain 16-bit decoded instructions. The far jump flushes this and forces a pipeline refill in 32-bit mode. It also loads CS with the correct 32-bit selector. If you omit it or delay it, you get a triple fault — the CPU resets.

Why No Interrupts?

In real mode, INT n looks up vector n in the IVT at address 0x0000. In protected mode, interrupts go through the IDT (Interrupt Descriptor Table). The moment you set PE=1, any interrupt that fires (even a hardware IRQ from the timer or keyboard) will look for your IDT — which you haven't set up yet. The result: triple fault, system reset. CLI before switching, set up your IDT after, then STI.
