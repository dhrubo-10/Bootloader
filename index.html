01 · Foundation

The Boot Process

What actually happens between pressing the power button and your OS running. Every layer, no hand-waving.

Power-On: The First Instruction

The moment power is applied, the CPU is in a known, hard-wired state. On x86, the instruction pointer CS:IP is set to 0xFFFF:0x0000, which in 16-bit real mode resolves to physical address 0xFFFF0. That's 16 bytes below the top of the first megabyte of address space.

At that address sits a JMP instruction — placed there by your motherboard firmware (BIOS or UEFI). It jumps to the actual firmware code, typically somewhere in the high flash ROM. The CPU has no idea what OS you're running. It doesn't care. It just executes the instruction at that address.

At reset, all general-purpose registers (EAX, EBX, etc.) are set to zero or undefined values. EFLAGS is cleared except for bit 1 (reserved, always 1). The CPU is running in 16-bit real mode — no memory protection, no virtual addressing, no privilege rings. Just raw segment:offset addressing with a 1 MB ceiling. The pipeline is flushed, caches are invalidated, and the branch predictor has no history. It's a completely cold start at the silicon level.

Why 0xFFFF0? After a reset, the CPU drives CS to 0xF000 with an internal base of 0xFFFF0000 (in 80386+). The real mode segment:offset pair 0xFFFF:0x0000 evaluates to 0xFFFF0. The first instructions are in ROM — ROM that exists at the top of the 1MB + a bit of extended space. On modern CPUs, this ROM is actually a small flash chip (SPI flash, typically 16–32 MB) soldered on the motherboard. The chipset maps a region of this flash into the top of the CPU's address space before any RAM is even initialized. The CPU is literally reading from flash storage on its very first instruction cycle.

Real Mode: The Starting Environment

Real mode is where every x86 CPU begins, no matter how modern. It's a 16-bit execution environment that mimics the original 8086 from 1978. Physical addresses are computed as (segment × 16) + offset, giving a maximum addressable range of 1 MB + 64 KB - 16 bytes (the infamous "High Memory Area"). There is no memory protection whatsoever — any code can read or write any physical address, including the IVT, BDA, or ROM regions. A single bad pointer dereference can silently corrupt the interrupt table and crash the machine with no error. This is the environment your bootloader lives in.

Register widths are 16-bit by default, but on 386+ CPUs you can use 32-bit operand and address size prefixes (0x66 and 0x67) even in real mode — a trick some bootloaders use to access memory above 64 KB within a segment without switching modes.

POST (Power-On Self Test)

Before anything useful happens, the BIOS runs POST. It's not magic — it's just a checklist:

  • Test CPU registers and basic instruction execution
  • Verify CMOS checksum (BIOS settings stored in battery-backed SRAM)
  • Initialize the memory controller and test RAM (that memory count you used to watch tick up)
  • Initialize buses: PCI, PCIe, USB
  • Enumerate and initialize hardware: IDE, SATA, NVMe controllers
  • Set up the Interrupt Vector Table (IVT) at address 0x0000

POST failures communicate through beep codes — because the video subsystem itself might not be initialized yet, there's no screen to write to. Each BIOS vendor (AMI, Award, Phoenix) has their own beep code scheme. One long beep + two short beeps means something different on AMI vs Award. On modern UEFI systems, POST errors are often logged to NVRAM and surfaced via debug LEDs or a small 7-segment display on enthusiast motherboards (the "POST code" display showing hex values like A2, 00).

The RAM test during POST is a destructive read-write-verify cycle across every addressable cell. The firmware writes known patterns (all zeros, all ones, alternating bits) and reads them back. This is why POST takes longer with more RAM — it's physically testing every bit. You can usually disable it in BIOS settings ("Quick Boot") which skips the full test and trusts that RAM is good.

UEFI vs Legacy BIOS POST: UEFI firmware runs a more structured initialization sequence called PI (Platform Initialization), divided into phases: SEC (Security), PEI (Pre-EFI Initialization), DXE (Driver eXecution Environment), BDS (Boot Device Selection), and RT (Runtime Services). Each phase has well-defined entry and exit conditions. DXE is where most hardware drivers run, and it's where the UEFI Shell and applications live. This is far more modular than legacy BIOS, which was essentially a single monolithic flat binary.

The Boot Device Search

After POST, the BIOS checks its configured boot order. It looks for a bootable device. For a disk, "bootable" is brutally simple: read the first 512 bytes. If the last two bytes are 0x55 and 0xAA — it's bootable. That's it. That's the entire check.

The BIOS reads the boot sector using INT 13h — a BIOS interrupt that provides disk I/O services in real mode. Early INT 13h used CHS (Cylinder-Head-Sector) geometry, which capped disk access at 8 GB. LBA (Logical Block Addressing) extensions to INT 13h (INT 13h AH=42h) removed this limit and are what modern bootloaders use. If you've written a bootloader with INT 13h AH=0x42 and a Disk Address Packet (DAP), you've used LBA extensions directly.

The 0x55AA signature is at bytes 510 and 511 (0-indexed), i.e., the last two bytes of the 512-byte sector. The BIOS loads those 512 bytes to address 0x7C00 and jumps to it. Your bootloader now has control. Note that bytes 446–509 of the MBR are the partition table — four 16-byte entries describing up to four primary partitions. Bytes 0–445 (446 bytes) are the only space available for your actual bootloader code. In practice it's even less if you include a BPB (BIOS Parameter Block) at the start, as FAT-formatted drives do.

Why 0x7C00?

The BIOS loads your MBR to physical address 0x7C00. Why this specific address? Historical accident. On the IBM PC (8088, 1981), this was the highest point where a 512-byte bootloader could live without overwriting itself or the BIOS data area, while still leaving the first 32KB for the OS. The original PC had 32KB of usable RAM. 0x7C00 = 0x8000 - 0x0200 (512 bytes).

There's a subtle bug trap here: 0x7C00 can be addressed as 0x0000:0x7C00 or 0x07C0:0x0000 — both resolve to the same physical address in real mode. If your bootloader uses [org 0x7C00] in NASM but the BIOS jumps to 0x07C0:0x0000, your absolute label addresses will be wrong by 0x7C00 and all your data references will be garbage. Always explicitly set DS to a known value at the start of your bootloader. Never assume segment register contents on entry — the BIOS spec doesn't guarantee them.

The A20 Line: On the original 8086, the address bus was 20 bits wide (A0–A19), giving exactly 1 MB. Programs that "wrapped around" past 1 MB (address 0x100000) would silently alias back to address 0x00000 — some programs relied on this behavior. When the 286 added a 21st address line (A20), IBM physically gated it through the keyboard controller (8042) and left it disabled by default to preserve backward compatibility. Your bootloader must enable A20 before accessing memory above 1 MB. There are multiple methods: keyboard controller method, Fast A20 via port 0x92, BIOS INT 15h AH=2401h, and more. Many bootloaders try all of them. If you forget, accessing address 0x100000 silently wraps to 0x00000 and you spend hours debugging memory corruption.

The Full Boot Sequence

1
CPU Reset
CPU sets CS:IP = 0xFFFF:0x0000. All registers zeroed or set to known state. Cache flushed. Running in 16-bit real mode.
2
BIOS/Firmware executes
JMP at 0xFFFF0 takes us to firmware. POST runs, hardware initialized, IVT populated at 0x0000. BIOS services become available via software interrupts.
3
Boot device selected
First 512 bytes of boot device read via INT 13h. 0x55AA signature verified. BIOS iterates boot order until a valid MBR is found.
4
MBR loaded to 0x7C00
BIOS does JMP 0x0000:0x7C00. We're in 16-bit real mode. CPU hands off to your code. DL register contains the boot drive number (0x80 for first HDD).
5
Stage 1 Bootloader
MBR code (≤446 bytes usable) loads a larger Stage 2 from disk. It reads the partition table, finds the active partition, and loads Stage 2 using INT 13h LBA reads. Stack is manually set up — typically below 0x7C00.
6
Stage 2: The real work
Enable A20. Query memory map via INT 15h E820h. Set up GDT. Switch to protected mode (set PE bit in CR0). Build page tables. Enable paging (set PG bit in CR0). Enter long mode (set LME in EFER MSR, then set CR4.PAE).
7
Kernel entry
Parse ELF headers. Load PT_LOAD segments to correct virtual addresses. Pass boot information structure (memory map, framebuffer info, ACPI tables pointer). Jump to kernel's entry point — now running in 64-bit long mode with paging active.

Protected Mode and the GDT

Before jumping to the kernel, Stage 2 must leave real mode behind. The switch to 32-bit protected mode requires setting up a Global Descriptor Table (GDT) — a data structure that defines memory segments with base, limit, and access rights. In protected mode, segment registers no longer hold raw base addresses; they hold selectors — 16-bit indices into the GDT.

A minimal GDT for a bootloader has three entries: a null descriptor (required by the CPU spec — accessing segment 0x0000 causes a General Protection Fault), a code segment (ring 0, executable, readable), and a data segment (ring 0, writable). The switch itself is a precise sequence: load the GDT with LGDT, set bit 0 of CR0 (the PE bit), then immediately perform a far jump to flush the instruction pipeline and reload CS with the new code segment selector. Miss any step and the CPU triple-faults — no error message, just an instant reset.

Long Mode (64-bit): Reaching 64-bit long mode from real mode requires going through protected mode first — you can't jump directly. The sequence: enable PAE (set CR4.PAE), load a valid PML4 page table into CR3, set the LME (Long Mode Enable) bit in the EFER MSR (via RDMSR/WRMSR on MSR 0xC0000080), then enable paging by setting CR0.PG. At this point the CPU enters "compatibility mode" — long mode is active but you're still running 32-bit code. A far jump to a 64-bit code segment selector (L-bit set in GDT) finally gets you into true 64-bit mode. This is why bootloaders are often a layered assembly of 16-bit, 32-bit, and 64-bit code sections in the same file.

The E820 Memory Map

Before leaving real mode, your bootloader should call INT 15h AH=E820h to get a memory map from the BIOS. This is the only reliable way to know which physical address ranges are usable RAM, which are reserved by hardware, which are ACPI tables, and which are flat-out holes. The call fills a structure with entries typed as: 1 = usable RAM, 2 = reserved, 3 = ACPI reclaimable, 4 = ACPI NVS (non-volatile sleep), 5 = bad memory. Your kernel's physical memory manager must respect this map — writing to a "reserved" region can corrupt firmware data structures or hardware MMIO registers. The E820 map is one of the most important pieces of information a bootloader hands to the kernel. Linux stores it and exposes it at /sys/firmware/memmap/.

02 · Foundation

Real Mode

The CPU's initial operating mode. 16-bit registers, segmented addressing, 1MB address space. Where you start.

What Real Mode Actually Is

When your CPU boots, it starts in real mode — the mode where the CPU behaves essentially like an 8086 from 1978. No memory protection. No privilege levels. No paging. Any code can read or write any memory, including the IVT and BIOS data area. It's raw hardware access.

You have 16-bit registers and you can only directly address 1 MB of memory. The reason for this limit: the address bus on the original 8086 was 20 bits wide. 2²⁰ = 1,048,576 bytes = 1 MB. Modern CPUs still start in this mode for backward compatibility.

Registers in Real Mode

Register(s) Name Width Purpose
AX, BX, CX, DX General Purpose 16-bit Arithmetic, data. Split into AH/AL, BH/BL etc. AX=accumulator, CX=counter, DX=data/I/O, BX=base.
SI, DI Index 16-bit Source Index, Destination Index. Used for string ops (MOVSB, LODSB etc.).
BP, SP Pointer 16-bit Base Pointer and Stack Pointer. BP references stack frame, SP tracks top of stack.
CS, DS, ES, SS Segment 16-bit Code, Data, Extra, Stack segments. Define 64KB windows into memory.
IP Instruction Pointer 16-bit Offset within CS segment. You can't directly write IP — only JMP/CALL/RET affect it.
FLAGS Flags Register 16-bit CF (carry), ZF (zero), SF (sign), OF (overflow), IF (interrupt enable), DF (direction).

Segmented Addressing: The Core Mechanic

Real mode uses a segment:offset addressing scheme. Physical address is computed as:

formula 
Physical Address = (Segment × 16) + Offset
                   = (Segment << 4) + Offset

Segment is shifted left by 4 bits (multiplied by 16), then the offset is added. Both are 16-bit values. The result is a 20-bit physical address.

Example: CS = 0x07C0, IP = 0x0000 → Physical = 0x07C0 × 16 + 0 = 0x07C00. This is why the BIOS often jumps to 0x07C0:0x0000 — same physical address as 0x0000:0x7C00.

Aliasing alert: Multiple segment:offset pairs map to the same physical address. 0x0000:0x7C00, 0x07C0:0x0000, and 0x07B0:0x0100 all point to physical 0x7C00. This matters when you call far procedures or rely on CS for data access.

Stack in Real Mode

The stack uses SS:SP. The x86 stack grows downward. PUSH decrements SP by 2 then writes. POP reads then increments. You need to set up your own stack — the BIOS gives you one but you shouldn't rely on it. Common setup:

x86 NASM · real mode stack setup 
; Set up stack at 0x0000:0x7BFF (just below our code)
cli                         ; Disable interrupts during stack setup
xor  ax, ax
mov  ss, ax               ; SS = 0x0000
mov  sp, 0x7C00            ; SP = 0x7C00 — stack grows down from here
sti                         ; Re-enable interrupts

Real Mode Limitations

  • Max 1 MB addressable — 20-bit address bus. Segment 0xFFFF + offset 0xFFFF = 0x10FFEF (wraps around!)
  • No memory protection — all code runs at the same privilege level. Any bug can overwrite interrupt vectors.
  • No multitasking — single flat execution context.
  • Max 64 KB per segment — 16-bit offset. You need multiple segments to access more.
  • BIOS interrupts only — the only way to talk to hardware (disk, video) is via BIOS INT calls.

A Minimal Real Mode Program

x86 NASM · minimal bootloader skeleton 
[BITS 16]
[ORG 0x7C00]

start:
    ; Clear segment registers — BIOS may leave them dirty
    cli
    xor  ax, ax
    mov  ds, ax
    mov  es, ax
    mov  ss, ax
    mov  sp, 0x7C00
    sti

    ; Print a character using BIOS INT 10h
    mov  ah, 0x0E        ; TTY output function
    mov  al, '!'
    int  0x10

.halt:
    hlt
    jmp  .halt          ; Loop in case of NMI waking us

; Padding and boot signature
times 510 - ($ - $$) db 0
dw 0xAA55              ; Note: little-endian, stored as 55 AA on disk
ORG directive: [ORG 0x7C00] tells NASM that this code will be loaded at offset 0x7C00. It doesn't move anything — it just adjusts address calculations for labels so jmp label generates the correct address.

446 bytes, not 512. If you're building a real bootloader, you have 446 bytes for code. The rest is partition table + signature. In practice, for a learning bootloader without a partition table, you get all 510 bytes — but the moment you add MBR partitioning, you lose 64 bytes.

The Boot Signature: 0x55AA

The last two bytes of the MBR must be 0x55 followed by 0xAA. In x86 little-endian storage, this means the 16-bit word at offset 0x1FE is 0xAA55. The BIOS checks this before jumping to 0x7C00. If it's wrong, the BIOS skips this device entirely.

Partition Table Entry Structure

partition entry · 16 bytes 
; Each partition entry is 16 bytes:
struc partition_entry
    .status      resb 1    ; 0x80 = bootable, 0x00 = not bootable
    .chs_start   resb 3    ; CHS address of first sector (legacy, mostly ignored)
    .type        resb 1    ; Partition type: 0x83=Linux, 0x0B=FAT32, 0x82=swap...
    .chs_end     resb 3    ; CHS address of last sector (legacy)
    .lba_start   resd 1    ; LBA of first sector (USE THIS, not CHS)
    .sector_cnt  resd 1    ; Total sectors in partition
endstruc

Why Stage 2 Is Necessary

446 bytes is not enough to load a kernel. You can't even implement a basic FAT32 driver in 446 bytes. The MBR's only job is to:

  • Find the active (bootable) partition
  • Read Stage 2 from a known location on disk into memory
  • Jump to Stage 2

Stage 2 can be as large as you want — typically loaded at 0x7E00 (right after the MBR in memory). It has the space to enable A20, set up the GDT, switch to 32-bit protected mode, parse the filesystem, and load the kernel.

A Real MBR: Loading Stage 2

x86 NASM · MBR loading stage 2 via LBA 
[BITS 16]
[ORG 0x7C00]

mbr_start:
    cli
    xor   ax, ax
    mov   ds, ax
    mov   es, ax
    mov   ss, ax
    mov   sp, 0x7C00
    sti
    mov   [boot_drive], dl  ; BIOS passes drive number in DL

    ; Load 4 sectors (2KB) starting at LBA 1, to 0x7E00
    mov   si, dap             ; DS:SI points to Disk Address Packet
    mov   ah, 0x42           ; INT 13h AH=0x42 = Extended Read (LBA)
    mov   dl, [boot_drive]
    int   0x13
    jc    disk_error          ; CF set on error

    jmp   0x0000:0x7E00       ; Far jump to Stage 2

disk_error:
    hlt

; Disk Address Packet (DAP) for INT 13h extended read
dap:
    db 0x10         ; Size of DAP = 16 bytes
    db 0x00         ; Reserved, must be 0
    dw 4            ; Number of sectors to read
    dw 0x7E00       ; Destination offset
    dw 0x0000       ; Destination segment
    dq 1            ; LBA of first sector to read (sector 1, right after MBR)

boot_drive:
    db 0

times 446 - ($ - $$) db 0   ; Pad to partition table
times 64 db 0               ; Empty partition table
dw 0xAA55
Key insight: Save the boot drive number from DL immediately. The BIOS passes it in DL before jumping to 0x7C00, but the moment you call any BIOS INT, DL may be clobbered. Store it and use it for all subsequent disk operations.
04 · BIOS & I/O

BIOS Interrupts

Your only interface to hardware in real mode. Know these cold — they're the API of 1981.

How INT Works

The x86 INT n instruction pushes FLAGS, CS, and IP onto the stack, then looks up vector n in the Interrupt Vector Table at physical address 0x0000. Each entry is 4 bytes: a 16-bit offset followed by a 16-bit segment. The CPU jumps to that segment:offset — that's the BIOS handler. IRET at the end pops CS, IP, and FLAGS, returning to your code.

The IVT occupies the first 1024 bytes of memory (256 vectors × 4 bytes). It lives at 0x0000:0x0000. You can actually overwrite BIOS interrupt handlers — but unless you're writing your own BIOS, don't.

INT 10h — Video Services

AH Function Input Output
0x00 Set video mode AL = mode (0x03 = 80×25 text, 0x12 = 640×480 VGA) —
0x0E TTY write char AL = char, BH = page, BL = color Cursor advances automatically
0x02 Set cursor pos BH = page, DH = row, DL = col —
0x0F Get video mode — AH = columns, AL = mode, BH = page
x86 NASM · print a null-terminated string 
; Input: SI = pointer to null-terminated string
print_str:
    push  ax
    push  bx
    mov   ah, 0x0E
    xor   bx, bx      ; Page 0, foreground color irrelevant in text mode
.loop:
    lodsb              ; AL = [DS:SI], SI++
    test  al, al       ; Check for null terminator
    jz    .done
    int   0x10
    jmp   .loop
.done:
    pop   bx
    pop   ax
    ret

INT 13h — Disk Services

AH Function Key Inputs
0x00 Reset disk controller DL = drive
0x02 Read sectors (CHS) AL=count, CH=cylinder, CL=sector(1-63), DH=head, DL=drive, ES:BX=buffer
0x41 Check INT 13h extensions BX=0x55AA, DL=drive → CF clear if supported
0x42 Extended Read (LBA) DS:SI = pointer to DAP (Disk Address Packet), DL=drive
0x48 Get drive parameters (ext) DS:SI = result buffer, DL=drive → geometry info
Always use LBA (INT 13h AH=0x42) not CHS (AH=0x02). CHS addressing breaks beyond 8 GB and the cylinder/head/sector encoding is a historical disaster. Check for extension support with AH=0x41 first, but any remotely modern BIOS supports it.

INT 15h — System Services

The most important function for bootloaders:

AX Function Purpose
0xE820 Get Memory Map The only reliable way to discover installed RAM. CRITICAL — do this before entering protected mode.
0xE801 Get Extended Memory Older method. Returns memory in 1KB and 64KB blocks. Less detailed than E820.

x86 NASM · INT 15h E820 memory map enumeration 
; Build a memory map at 0x8000
; Returns: [0x8004] = number of entries
get_memory_map:
    xor   ebx, ebx       ; EBX = 0 for first call, BIOS fills continuation value
    xor   bp, bp         ; BP = entry count
    mov   es, bp
    mov   di, 0x8000      ; Write entries starting at ES:DI = 0x8000
    mov   edx, 0x0534D4150 ; Magic: "SMAP"
.loop:
    mov   eax, 0xE820      ; Function number
    mov   [es:di + 20], dword 1  ; ACPI 3.0 extended attributes field
    mov   ecx, 24          ; Entry size in bytes
    int   0x15
    jc    .done            ; CF set = error or end
    cmp   eax, 0x0534D4150 ; BIOS must return "SMAP" in EAX
    jne   .done
    test  ecx, ecx
    jz    .skip
    inc   bp              ; Count this entry
    add   di, 24           ; Advance buffer pointer
.skip:
    test  ebx, ebx
    jz    .done            ; EBX = 0 means last entry
    jmp   .loop
.done:
    mov   [0x8004], bp     ; Store count for kernel
    ret
05 · BIOS & I/O

Disk I/O

CHS vs LBA. Reading sectors. Writing reliable disk code that doesn't silently corrupt.

CHS: The Legacy You Must Know

CHS stands for Cylinder, Head, Sector. It's how ancient hard drives physically addressed data:

  • Cylinder: Concentric ring on the disk platter (0 to N-1)
  • Head: Read/write head on the arm (0 to N-1)
  • Sector: Pie-slice of a track — 1-indexed, starts at 1, not 0

CHS was already broken by the early 1990s. INT 13h CHS only supports 10-bit cylinders, 8-bit heads, 6-bit sectors — max ~8 GB. For anything modern, use LBA.

LBA: Logical Block Addressing

LBA treats the disk as a flat array of 512-byte (or 4096-byte) sectors numbered from 0. Sector 0 is the MBR. Sector 1 is the first sector after the MBR. Simple. The conversion from LBA to CHS if you ever need it:

formula · LBA to CHS conversion 
sector    = (LBA % sectors_per_track) + 1
head      = (LBA / sectors_per_track) % num_heads
cylinder  = (LBA / sectors_per_track) / num_heads

Disk Address Packet (DAP)

INT 13h extended read (AH=0x42) takes a pointer to a DAP in DS:SI. The DAP structure:

x86 NASM · DAP structure 
; Disk Address Packet — 16 bytes
struc DAP
    .size         resb 1  ; Size of this structure = 0x10 (16)
    .reserved     resb 1  ; Must be 0
    .count        resw 1  ; Number of sectors to transfer (max ~127)
    .offset       resw 1  ; Transfer buffer offset
    .segment      resw 1  ; Transfer buffer segment
    .lba_lo       resd 1  ; Low 32 bits of 64-bit LBA
    .lba_hi       resd 1  ; High 32 bits (0 for drives <2TB)
endstruc

Robust Disk Read with Retries

Disks fail. BIOS disk functions fail. Always retry. The standard approach: try up to 3 times, reset the controller between attempts.

x86 NASM · disk read with retry 
; Input: SI = DAP pointer, DL = drive number
; Trashes: AX
disk_read:
    mov   cx, 3             ; Retry count
.retry:
    push  cx
    mov   ah, 0x42          ; Extended read
    int   0x13
    pop   cx
    jnc   .success          ; CF clear = success

    ; Read failed — reset controller and retry
    push  cx
    mov   ah, 0x00          ; Reset disk controller
    int   0x13
    pop   cx
    loop  .retry

    ; All retries failed
    jmp   disk_error

.success:
    ret
Reading across a 64KB segment boundary will fail or corrupt data. The BIOS DMA for disk reads can't cross a 64KB segment boundary. If your destination buffer is at 0x7F00 and you read 512 bytes (0x200), you end up at 0x8100 — which crosses the 0x8000 boundary if DS=0. Keep reads within a single 64KB segment or split them.

Loading a Large Bootloader: The Strategy

Your Stage 2 can be loaded anywhere in the first 640 KB (0x0000–0x9FFFF). Common choices:

  • 0x7E00 — Right after MBR. Simple. Stage 2 can be up to ~480 KB here before hitting the EBDA at 0x80000.
  • 0x10000 — 64 KB mark. Clean alignment, plenty of space below 0x80000.
  • 0x20000 — 128 KB mark. Used by some bootloaders to keep away from the IVT/BDA region entirely.
06 · 32-bit Transition

The A20 Line

The most absurd hardware hack in computing history. You must deal with it.

The Problem: Wrap-Around Compatibility

On the 8086, the address bus was 20 bits. Accessing address 0xFFFF:0x0010 computes to 0x100000 (1MB + 16 bytes). But with a 20-bit bus, bit 20 doesn't exist — the address wraps around to 0x00000. Some programs (mostly DOS ones) relied on this wrap-around behavior.

When the 286 arrived with a 24-bit address bus, bit 20 (A20) existed. The wrap-around no longer happened. This broke compatibility. IBM's engineers — in an act of legendary hackery — added a hardware gate on the A20 line, connected to bit 1 of the PS/2 keyboard controller's output port. By default, A20 was disabled (gated off), so the 8086 wrap-around was preserved.

The result: every x86 PC since the 80286 has had this bizarre keyboard-controller-managed address line. You must enable A20 before you can access memory above 1MB in protected mode.

Three Ways to Enable A20

Method 1: BIOS INT 15h

x86 NASM · A20 via BIOS 
mov   ax, 0x2401     ; INT 15h AX=0x2401: Enable A20
int   0x15
jc    .try_keyboard  ; CF set = not supported, try keyboard method

Method 2: Keyboard Controller (the original hack)

x86 NASM · A20 via keyboard controller (Port 0x64/0x60) 
enable_a20_kbd:
    call  kbd_wait_cmd
    mov   al, 0xAD        ; Disable PS/2 port 1 (keyboard)
    out   0x64, al

    call  kbd_wait_cmd
    mov   al, 0xD0        ; Read output port command
    out   0x64, al

    call  kbd_wait_data
    in    al, 0x60        ; Read current output port value
    push  ax              ; Save it

    call  kbd_wait_cmd
    mov   al, 0xD1        ; Write output port command
    out   0x64, al

    call  kbd_wait_cmd
    pop   ax
    or    al, 0x02        ; Set bit 1 = A20 enable
    out   0x60, al        ; Write new output port value

    call  kbd_wait_cmd
    mov   al, 0xAE        ; Re-enable PS/2 port 1
    out   0x64, al
    ret

kbd_wait_cmd:            ; Wait for keyboard controller to be ready for a command
    in    al, 0x64
    test  al, 0x02        ; Bit 1: input buffer full
    jnz   kbd_wait_cmd
    ret

Method 3: Fast A20 (Port 0x92)

x86 NASM · Fast A20 via Port 0x92 
enable_a20_fast:
    in    al, 0x92
    test  al, 0x02        ; Already enabled?
    jnz   .done
    or    al, 0x02
    and   al, 0xFE        ; Clear bit 0 — don't trigger fast reset!
    out   0x92, al
.done:
    ret
Bit 0 of Port 0x92 is the fast reset bit. Setting it reboots the machine. When setting bit 1 (A20), always clear bit 0 first. Getting this wrong means your machine hard-resets the moment you try to enable A20.

Verifying A20 Is Enabled

After enabling, verify it actually worked. Write a known value to a real-mode accessible address, then write a different value to the same physical address via the ≥1MB path. If A20 is still disabled, both accesses alias to the same location. If it's enabled, they're different.

x86 NASM · A20 verification 
; Returns: ZF set if A20 disabled, clear if enabled
check_a20:
    push  es
    push  di
    push  ds
    push  si

    xor   ax, ax
    mov   es, ax
    mov   di, 0x0500      ; ES:DI = 0x0000:0x0500 = physical 0x0500

    mov   ax, 0xFFFF
    mov   ds, ax
    mov   si, 0x0510      ; DS:SI = 0xFFFF:0x0510 = physical 0x100500

    mov   al, [es:di]
    push  ax              ; Save original values
    mov   al, [ds:si]
    push  ax

    mov   byte [es:di], 0x00
    mov   byte [ds:si], 0xFF

    cmp   byte [es:di], 0xFF  ; If equal: A20 off (both alias same address)

    pop   ax               ; Restore values
    mov   [ds:si], al
    pop   ax
    mov   [es:di], al

    pop   si
    pop   ds
    pop   di
    pop   es
    ret
07 · 32-bit Transition

Global Descriptor Table

The hardware data structure that defines memory segments in protected mode. Get this right or triple-fault immediately.

What the GDT Is

In protected mode, segment registers no longer contain physical addresses. They contain selectors — indices into the Global Descriptor Table. The GDT is an array of 8-byte segment descriptors that define the base address, limit, and access rights of each memory segment. The CPU hardware enforces these limits and permissions.

The first entry (index 0) is always the null descriptor — 8 bytes of zeros. Loading any segment register with selector 0 that gets dereferenced causes a General Protection Fault. This is intentional: it catches uninitialized segment register bugs.

Segment Descriptor Layout

Each descriptor is 8 bytes. The layout is intentionally scrambled — historical byte-level compatibility reasons with the 286's 6-byte descriptor format:

segment descriptor · bit layout (8 bytes) 
Bits 63-56:  Base[31:24]       High byte of base address
Bits 55-52:  Flags             G, D/B, L, AVL
Bits 51-48:  Limit[19:16]      High nibble of limit
Bits 47-40:  Access Byte       P, DPL, S, Type
Bits 39-16:  Base[23:0]        Low 3 bytes of base address
Bits 15-0:   Limit[15:0]       Low word of limit

Access Byte breakdown (byte 5):
  Bit 7:   P   — Present (must be 1 for valid descriptor)
  Bits 6-5: DPL — Descriptor Privilege Level (0=kernel, 3=user)
  Bit 4:   S   — Descriptor type (1=code/data, 0=system)
  Bit 3:   E   — Executable (1=code, 0=data)
  Bit 2:   DC  — Direction/Conforming
  Bit 1:   RW  — Readable(code)/Writable(data)
  Bit 0:   A   — Accessed (CPU sets this, you leave it 0)

Flags nibble (bits 55-52):
  Bit 55:  G   — Granularity (0=byte limit, 1=page (4KB) limit)
  Bit 54:  D/B — Default op size (0=16-bit, 1=32-bit)
  Bit 53:  L   — Long mode (1=64-bit code segment)
  Bit 52:  AVL — Available for OS use

A Minimal 32-bit GDT

For a flat 32-bit protected mode setup, you need exactly 3 entries: null descriptor, code segment, data segment.

x86 NASM · GDT for 32-bit protected mode 
gdt_start:

; Descriptor 0: Null — mandatory
gdt_null:
    dq 0

; Descriptor 1: Code segment (selector 0x08)
; Base=0x00000000, Limit=0xFFFFF (×4KB = 4GB), Ring 0, 32-bit
gdt_code:
    dw 0xFFFF     ; Limit[15:0]
    dw 0x0000     ; Base[15:0]
    db 0x00       ; Base[23:16]
    db 0x9A       ; Access: P=1 DPL=00 S=1 E=1 DC=0 RW=1 A=0 → 10011010
    db 0xCF       ; Flags+Limit[19:16]: G=1 D=1 L=0 → 1100 | 1111
    db 0x00       ; Base[31:24]

; Descriptor 2: Data segment (selector 0x10)
; Same span as code, but not executable, writable
gdt_data:
    dw 0xFFFF
    dw 0x0000
    db 0x00
    db 0x92       ; Access: P=1 DPL=00 S=1 E=0 DC=0 RW=1 A=0 → 10010010
    db 0xCF
    db 0x00

gdt_end:

; GDT Descriptor (for LGDT instruction)
gdt_descriptor:
    dw gdt_end - gdt_start - 1  ; Limit: size in bytes minus 1
    dd gdt_start                  ; Base: linear address of GDT

; Segment selectors (index × 8, RPL in bits 1:0)
CODE_SEG equ gdt_code - gdt_start  ; = 0x08
DATA_SEG equ gdt_data - gdt_start  ; = 0x10

Segment Selectors: What CS/DS Actually Contain

bits 15:3
Index
bit 2
TI
bits 1:0
RPL
  • Index: Which entry in the GDT (or LDT if TI=1). Entry 1 = index 1 = bits 15:3 = 0x0008. Entry 2 = 0x0010.
  • TI (Table Indicator): 0 = GDT, 1 = LDT (Local Descriptor Table).
  • RPL (Requested Privilege Level): 0 = ring 0, 3 = ring 3. CPU enforces that RPL ≤ descriptor's DPL.
The flat model: Setting both code and data segments to base 0 and limit 4GB (with G=1, limit=0xFFFFF → 0xFFFFF × 4096 = 4GB) means segment registers become irrelevant — you're using a flat address space. This is what every modern OS does. The segmentation hardware is effectively bypassed in favor of paging.
08 · 32-bit Transition

Protected Mode

The switch from 16-bit chaos to 32-bit hardware-enforced memory protection. One bit in CR0. Then a lot of careful work.

What Changes in Protected Mode

  • 32-bit registers — EAX, EBX, ECX, EDX, ESI, EDI, ESP, EBP, EIP
  • Up to 4 GB addressable — with 32-bit registers and a 32-bit address bus
  • Segment registers are selectors — they index into the GDT, not direct memory addresses
  • Memory protection — the CPU enforces segment limits and privilege levels
  • No BIOS interrupts — INT calls go through your IDT, not the IVT. BIOS services are real-mode only.

CR0: Control Register 0

CR0 is a 32-bit control register. Bit 0 (PE — Protection Enable) is the on/off switch for protected mode. Setting it is the actual transition. There's no going back easily (well, technically you can, but that's obscure).

bit 31
PG
bits 30:19
reserved
bit 18
AM
bit 16

bits 5:0
NE,ET,TS,EM,MP
bit 0

The Exact Switching Sequence

This is the exact order you must follow. Deviate and you triple-fault:

x86 NASM · real mode → protected mode transition 
[BITS 16]

enter_protected_mode:
    ; Step 1: Disable interrupts — no BIOS interrupts in PM
    cli

    ; Step 2: Load GDT — must be done before setting PE bit
    lgdt  [gdt_descriptor]

    ; Step 3: Set PE bit in CR0
    mov   eax, cr0
    or    eax, 0x1          ; Set bit 0 (PE)
    mov   cr0, eax

    ; Step 4: FAR JUMP to flush instruction pipeline and reload CS
    ; The far jump MUST come immediately after setting PE
    ; It loads CS with our 32-bit code segment selector
    jmp   CODE_SEG:pm_entry    ; CODE_SEG = 0x08

[BITS 32]

pm_entry:
    ; Step 5: Update all other segment registers
    ; They still contain old real-mode values
    mov   ax, DATA_SEG         ; DATA_SEG = 0x10
    mov   ds, ax
    mov   es, ax
    mov   fs, ax
    mov   gs, ax
    mov   ss, ax

    ; Step 6: Set up a proper 32-bit stack
    mov   esp, 0x90000       ; Stack at 576 KB mark

    ; We are now in 32-bit protected mode
    ; Full 32-bit registers, hardware-enforced segments
The far jump is mandatory. After setting PE, the CPU's instruction prefetch queue may contain 16-bit decoded instructions. The far jump flushes this and forces a pipeline refill in 32-bit mode. It also loads CS with the correct 32-bit selector. If you omit it or delay it, you get a triple fault — the CPU resets.

Why No Interrupts?

In real mode, INT n looks up vector n in the IVT at address 0x0000. In protected mode, interrupts go through the IDT (Interrupt Descriptor Table). The moment you set PE=1, any interrupt that fires (even a hardware IRQ from the timer or keyboard) will look for your IDT — which you haven't set up yet. The result: triple fault, system reset. CLI before switching, set up your IDT after, then STI.

Memory Map (E820)

Before entering protected mode, ask the BIOS what RAM actually exists. Your kernel needs this to manage memory.

Why You Need E820

The physical address space is not a flat array of usable RAM. It has holes — regions mapped to video memory, ROM, MMIO for devices, reserved firmware regions, ACPI tables. You cannot just assume everything from 0 to 4GB is RAM. Your kernel's physical memory manager must know which regions are safe to use.

INT 15h E820 is the definitive way to get this map. It returns a list of entries, each describing a physical address range and its type. You must call this in real mode — before entering protected mode.

E820 Entry Structure

C · E820 entry structure (20 or 24 bytes) 
struct e820_entry {
    uint64_t base;      // Physical base address of this region
    uint64_t length;    // Length in bytes
    uint32_t type;      // Region type (see below)
    uint32_t acpi_attr; // ACPI 3.0 extended attributes (optional)
} __attribute__((packed));

// Region types:
// 1 = Usable RAM               <-- the good stuff
// 2 = Reserved                 <-- hardware, firmware, don't touch
// 3 = ACPI Reclaimable         <-- usable after parsing ACPI tables
// 4 = ACPI NVS                 <-- ACPI non-volatile storage, never touch
// 5 = Bad RAM                  <-- defective memory, never use

Passing the Map to Your Kernel

Collect all E820 entries into a buffer (typically stored at a fixed address like 0x8000). Store the entry count. Then, when you jump to your kernel, pass this information either through:

  • Registers: put the map address in a register before jumping (simple but inflexible)
  • A boot info structure: create a struct at a fixed address with the map pointer, entry count, kernel command line, etc. This is what Multiboot and Linux's boot protocol do.
C · kernel-side E820 processing 
void parse_memory_map(struct e820_entry *entries, uint32_t count) {
    uint64_t total_usable = 0;
    
    for (uint32_t i = 0; i < count; i++) {
        if (entries[i].type == 1) {  // Usable RAM
            total_usable += entries[i].length;
            pmm_add_region(entries[i].base, entries[i].length);
        }
    }
    
    kprintf("Total usable RAM: %llu MB\n", total_usable / (1024 * 1024));
}
10 · Memory & Kernel

Paging

The second layer of address translation. Virtual addresses → physical addresses. How modern OSes isolate processes.

Why Paging Exists

Segmentation alone isn't enough for a modern OS. Paging adds a second layer of address translation that enables:

  • Virtual address spaces — each process thinks it has all of memory to itself
  • Memory isolation — process A can't read process B's pages (different page tables)
  • Demand paging — pages don't need to be in RAM (they can be on disk, swapped in when accessed)
  • Memory-mapped files — files appear as memory regions

32-bit Paging: Two-Level Page Tables

In 32-bit protected mode, a virtual address is split into three parts:

bits 31:22
Dir Index (10 bits)
bits 21:12
Table Index (10 bits)
bits 11:0
Page Offset (12 bits)
  • Page Directory: 1024 entries × 4 bytes = 4 KB. CR3 points here. Each entry points to a Page Table.
  • Page Table: 1024 entries × 4 bytes = 4 KB. Each entry gives the physical base of a 4 KB page.
  • Page Offset: 12 bits = 4096 bytes = 4 KB page size. Added directly to the page base.

Total: 1024 directories × 1024 tables × 4 KB = 4 GB addressable. Perfect for 32-bit.

Page Table Entry Format

bits 31:12
Physical Frame Number
bits 11:9
Avail
bit 7
PS
bit 5
A
bit 4
PCD
bit 2
U/S
bit 1
R/W
bit 0
P
  • P (Present): If 0, accessing this page causes a page fault.
  • R/W: 0 = read-only, 1 = read/write.
  • U/S: 0 = supervisor (ring 0 only), 1 = user accessible.
  • A (Accessed) / D (Dirty): CPU sets these automatically. Dirty = page was written.

Identity Mapping: Bootstrap Trick

When you first enable paging, the CPU is executing code at some physical address (say 0x10000). If virtual address ≠ physical address after enabling paging, your next instruction fetch will fault. Solution: identity map the first N MB — map virtual address X to physical address X. Then your code keeps running. After the kernel is loaded and has its own mappings, you can remove the identity map.

x86 NASM · enable paging (identity mapped first 4 MB) 
[BITS 32]

setup_paging:
    ; Page directory at 0x1000, page table at 0x2000
    ; Both must be 4 KB aligned

    ; Clear page directory (4 KB = 1024 dwords)
    mov   edi, 0x1000
    mov   ecx, 1024
    xor   eax, eax
    rep   stosd

    ; First PDE: points to our page table at 0x2000
    ; Flags: Present(1), Writable(1), Supervisor(0)
    mov   dword [0x1000], 0x2003    ; 0x2000 | P | R/W

    ; Fill page table: identity map 0x0 to 0x400000 (4 MB)
    mov   edi, 0x2000               ; Page table base
    xor   eax, eax
.fill_pt:
    mov   [edi], eax
    or    dword [edi], 0x3          ; Present + Writable
    add   eax, 0x1000              ; Next 4KB physical frame
    add   edi, 4
    cmp   eax, 0x400000            ; Mapped 4 MB yet?
    jb    .fill_pt

    ; Load CR3 with the page directory address
    mov   eax, 0x1000
    mov   cr3, eax

    ; Enable paging: set PG bit (bit 31) in CR0
    mov   eax, cr0
    or    eax, 0x80000000
    mov   cr0, eax
    ret
11 · Memory & Kernel

Long Mode (64-bit)

x86-64. The final destination for a modern OS kernel. 4-level page tables. 64-bit registers. The full deal.

Prerequisites for Long Mode

You can't jump straight to 64-bit from real mode. The CPU enforces a specific sequence:

  • You must be in 32-bit protected mode with paging enabled
  • The CPU must support long mode (check with CPUID)
  • You must set up 4-level page tables (PML4)
  • Enable Physical Address Extension (PAE, CR4 bit 5)
  • Set the LME bit in the EFER MSR (Model Specific Register)
  • Then set PG in CR0 — this activates long mode

Check for Long Mode Support

x86 NASM · CPUID long mode check 
[BITS 32]

check_long_mode:
    ; First check if CPUID supports extended functions
    mov   eax, 0x80000000
    cpuid
    cmp   eax, 0x80000001    ; Must support at least 0x80000001
    jb    .no_long_mode

    ; Get extended feature flags
    mov   eax, 0x80000001
    cpuid
    test  edx, 1 << 29       ; Bit 29 of EDX = LM (Long Mode)
    jz    .no_long_mode
    ret                       ; Long mode supported

.no_long_mode:
    ; Halt — this CPU can't run a 64-bit kernel
    hlt

64-bit Page Tables: 4-Level PML4

Long mode uses a 4-level page table structure. A 64-bit virtual address is split as:

bits 63:48
Sign Ext.
bits 47:39
PML4 (9)
bits 38:30
PDPT (9)
bits 29:21
PD (9)
bits 20:12

bits 11:0

4 levels × 9 bits + 12 offset = 48 bits of virtual address space = 256 TB. Physical address space with current CPUs: 48 bits = 256 TB physical RAM (not that you'll have that much).

The Full Long Mode Entry Sequence

x86 NASM · 32-bit protected mode → 64-bit long mode 
[BITS 32]

enter_long_mode:
    ; 1. Build minimal identity-mapped page tables
    ;    PML4 at 0x1000, PDPT at 0x2000, PD at 0x3000
    ;    Using 2MB huge pages — simpler, fewer tables

    mov   edi, 0x1000
    mov   cr3, edi
    xor   eax, eax
    mov   ecx, 3072           ; Clear 3 tables (3 × 4KB)
    rep   stosd

    ; PML4[0] → PDPT at 0x2000
    mov   dword [0x1000], 0x2003   ; Present + R/W
    ; PDPT[0] → PD at 0x3000
    mov   dword [0x2000], 0x3003
    ; PD[0] → 0x0 (2MB huge page)
    mov   dword [0x3000], 0x83     ; Present + R/W + PS (huge page)

    ; 2. Enable PAE (Physical Address Extension) in CR4
    mov   eax, cr4
    or    eax, 1 << 5            ; Bit 5 = PAE
    mov   cr4, eax

    ; 3. Set LME bit in EFER MSR (MSR 0xC0000080)
    mov   ecx, 0xC0000080
    rdmsr                          ; Read EFER → EDX:EAX
    or    eax, 1 << 8             ; Bit 8 = LME (Long Mode Enable)
    wrmsr                          ; Write back

    ; 4. Enable paging (PG bit) — activates long mode
    mov   eax, cr0
    or    eax, 0x80000000
    mov   cr0, eax

    ; 5. Far jump with 64-bit code segment selector
    ;    GDT needs a 64-bit code descriptor (L=1, D=0)
    jmp   CODE64_SEG:lm_entry

[BITS 64]
lm_entry:
    ; We are in 64-bit long mode
    ; Full 64-bit registers: RAX, RBX, RCX, RDX, RSI, RDI, R8-R15
    mov   rsp, 0x200000       ; Stack at 2 MB mark
The 64-bit GDT descriptor for the code segment needs L=1 (Long mode) and D=0 (NOT 32-bit default). The descriptor's base and limit are ignored in long mode — the CPU uses flat 64-bit addressing. You still need the descriptor structure, but only the type and L/D bits matter.

ELF & Kernel Loading

Your kernel is an ELF binary. Parse it. Load its segments. Jump to its entry point.

ELF: Executable and Linkable Format

ELF is the standard binary format on Linux and most Unix-like systems. Your kernel, compiled with GCC/Clang, produces an ELF file. The bootloader's job is to parse this file and load the correct segments into memory at the correct addresses.

ELF File Structure

1
ELF Header (52 bytes for 32-bit, 64 bytes for 64-bit)
Magic bytes \x7FELF, architecture, entry point address, offset to program headers.
2
Program Headers (segments)
Each entry says: load this chunk of the file to this virtual address, with these permissions.
3
Section Headers
Used by the linker and debugger. Your bootloader doesn't need these — use program headers.

The ELF64 Header

C · ELF64 structures 
typedef struct {
    uint8_t  e_ident[16];  // Magic: 7F 45 4C 46 (7F 'E' 'L' 'F'), class, endian...
    uint16_t e_type;       // 2=ET_EXEC (executable), 3=ET_DYN (shared)
    uint16_t e_machine;    // 0x3E = AMD64 (x86-64)
    uint32_t e_version;    // Must be 1
    uint64_t e_entry;      // Entry point virtual address — JUMP HERE
    uint64_t e_phoff;      // Offset of program header table
    uint64_t e_shoff;      // Offset of section header table (ignore this)
    uint32_t e_flags;
    uint16_t e_ehsize;     // Size of this header = 64
    uint16_t e_phentsize;  // Size of one program header entry = 56
    uint16_t e_phnum;      // Number of program header entries
    uint16_t e_shentsize;
    uint16_t e_shnum;
    uint16_t e_shstrndx;
} Elf64_Ehdr;

typedef struct {
    uint32_t p_type;    // 1=PT_LOAD (must be loaded), 0=PT_NULL (skip)
    uint32_t p_flags;   // PF_X(1)=exec, PF_W(2)=write, PF_R(4)=read
    uint64_t p_offset;  // Offset in ELF file where this segment starts
    uint64_t p_vaddr;   // Virtual address to load segment at
    uint64_t p_paddr;   // Physical address (usually same as vaddr)
    uint64_t p_filesz;  // Size in file (may be smaller than p_memsz)
    uint64_t p_memsz;   // Size in memory (zero the difference: BSS)
    uint64_t p_align;   // Alignment (must be power of 2)
} Elf64_Phdr;
p_filesz vs p_memsz: The BSS segment (uninitialized globals) takes no space in the file (p_filesz = 0) but needs space in memory (p_memsz > 0). When loading a PT_LOAD segment, copy p_filesz bytes from the file, then memset the remaining p_memsz - p_filesz bytes to zero. Miss this and your kernel's global variables start with garbage.

Kernel Loader: The Core Loop

C · ELF64 kernel loader 
typedef void (*KernelEntry)(struct BootInfo*);

void load_kernel(uint8_t *elf_data, struct BootInfo *boot_info) {
    Elf64_Ehdr *ehdr = (Elf64_Ehdr*)elf_data;

    // Verify ELF magic: 0x7F 'E' 'L' 'F'
    if (ehdr->e_ident[0] != 0x7F || ehdr->e_ident[1] != 'E' ||
        ehdr->e_ident[2] != 'L'  || ehdr->e_ident[3] != 'F') {
        panic("Not an ELF binary");
    }

    // Walk program headers, load all PT_LOAD segments
    Elf64_Phdr *phdr = (Elf64_Phdr*)(elf_data + ehdr->e_phoff);

    for (int i = 0; i < ehdr->e_phnum; i++, phdr++) {
        if (phdr->p_type != 1) continue;  // Not PT_LOAD, skip

        uint8_t *src  = elf_data + phdr->p_offset;
        uint8_t *dest = (uint8_t*)phdr->p_paddr;

        // Copy file data
        memcpy(dest, src, phdr->p_filesz);

        // Zero the BSS area (memsz > filesz)
        memset(dest + phdr->p_filesz, 0, phdr->p_memsz - phdr->p_filesz);
    }

    // Cast entry point to function pointer and call it
    KernelEntry entry = (KernelEntry)ehdr->e_entry;
    entry(boot_info);  // Should never return
    panic("Kernel returned!");
}
13 · Modern

UEFI

The modern firmware interface. More powerful than BIOS but also significantly more complex.

UEFI vs BIOS: What Actually Changed

UEFI (Unified Extensible Firmware Interface) replaces BIOS. Key differences:

  • Starts in 32 or 64-bit mode — no more 16-bit real mode gymnastics
  • Full C API — instead of INT calls, you call function pointers in a table
  • Filesystem understanding — UEFI natively reads FAT32. Your bootloader is an EFI application stored as a file.
  • GPT partitioning — UEFI uses GPT instead of MBR. No 512-byte size constraint.
  • Secure Boot — firmware verifies the bootloader's signature before running it.

UEFI Boot Process

1
SEC (Security) Phase
Firmware integrity check, CPU cache-as-RAM initialization, microcode update.
2
PEI (Pre-EFI Init)
Memory controller initialization. RAM brought online. Basic hardware init.
3
DXE (Driver Execution Environment)
UEFI drivers loaded. Boot services installed. All hardware initialized.
4
BDS (Boot Device Select)
UEFI looks for \EFI\BOOT\BOOTX64.EFI on the FAT32 EFI System Partition (ESP).
5
Your UEFI application runs
UEFI loads your .efi file (a PE32+ binary), calls its entry point in a full 64-bit environment.
6
ExitBootServices()
You call this to take ownership of hardware. UEFI firmware stops managing memory. You're on your own.

The UEFI Table Hierarchy

Everything in UEFI goes through function pointer tables:

C · UEFI entry point and table access 
// Your UEFI app's entry point — called by firmware
EFI_STATUS EFIAPI efi_main(
    EFI_HANDLE        ImageHandle,
    EFI_SYSTEM_TABLE  *SystemTable    // The root of everything
) {
    // Print via Boot Services → ConOut
    SystemTable->ConOut->OutputString(
        SystemTable->ConOut,
        L"Bootloader starting...\r\n"   // UTF-16LE strings in UEFI
    );

    // Get memory map before ExitBootServices
    UINTN                MemMapSize = 0;
    EFI_MEMORY_DESCRIPTOR *MemMap;
    UINTN                MapKey, DescSize;
    UINT32               DescVer;

    // First call gets required buffer size
    SystemTable->BootServices->GetMemoryMap(
        &MemMapSize, NULL, &MapKey, &DescSize, &DescVer
    );

    // Allocate + fetch the actual map
    SystemTable->BootServices->AllocatePool(
        EfiLoaderData, MemMapSize, (VOID**)&MemMap
    );
    SystemTable->BootServices->GetMemoryMap(
        &MemMapSize, MemMap, &MapKey, &DescSize, &DescVer
    );

    // Hand control to yourself — firmware no longer manages hardware
    SystemTable->BootServices->ExitBootServices(ImageHandle, MapKey);

    // Set up page tables, load kernel, jump to entry...
    load_and_run_kernel(MemMap, MemMapSize / DescSize);

    return EFI_SUCCESS; // Never reached
}

For learning purposes: Start with BIOS/MBR. It's harder in some ways (real mode, 512 bytes) but you understand every single layer. Once you've written a BIOS bootloader from scratch, UEFI's complexity makes sense — it's solving the same problems at a higher level. Projects like TianoCore EDK II and gnu-efi give you the headers and libraries to write UEFI apps without reimplementing the entire spec.

Recommended Learning Path

  • Write a BIOS MBR that prints a string → understand 16-bit real mode cold
  • Add Stage 2 that loads from disk and enters 32-bit protected mode
  • Add E820 memory map collection
  • Set up paging, enter long mode
  • Parse an ELF kernel, load it, jump to it
  • Then, and only then, write a UEFI version — you'll appreciate what it's abstracting
